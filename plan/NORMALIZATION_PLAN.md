# NORMALIZATION_PLAN — Table ownership renames + "entry point" → "module content"

Status: **IMPLEMENTED** (2026-09-29; `mvn verify` 81 green incl. smoke test, `npm test` 128 green, `npm run build` exit 0)
Scope: schema (Flyway V26/V27), backend (packages/classes/API/JSON keys), frontend (types/URLs),
i18n seed + migration, docs. Historical migrations and `docs/archive/**` are untouched.

## 0. Context and locked decisions

The portal migrated from a decommissioned Node implementation; several table names and the
"entry point" wording no longer reflect Crosshubber's model. Ownership of each table was
audited (Java package placement, FK structure, API consumers) and the following decisions
were made:

| # | Decision | Choice |
|---|---|---|
| D0a | Prefix style | `registry_` **underscore** (snake_case, matches repo; hyphen needs quoted identifiers everywhere) |
| D0b | Which tables get `registry_` prefix | `modules`, `module_versions` only; `entry_points` is handled by the module-content rename (D0e) |
| D0c | `entry_point_groups` owner | **Navigation module** — no `module_key` FK; it is pure shell-tree structure (categories, parent/child, sort, roles, hidden flag). Physically parked under `modules.registry.entrypointgroups` today; README architecture already draws EntryPts/Groups under **Nav**, not Registry |
| D0d | `workspaces` owner | **NOT navigation** — separate top-level feature (`com.crosshubber.portal.workspaces`). Table name stays `workspaces`. It only *references* content refs inside its JSONB `layout`/`groups` |
| D0e | Rename depth for entry-point wording | **Full**: tables + code identifiers + API paths + JSON keys + docs |
| D0f | `entry_points` table name | `registry_module_contents` |
| D0g | `instance_settings` scope | Only navigation settings today (`homeApp`, `pinnedAppsEnabled`, `workspacesEnabled`); rename to `navigation_settings` **and** move Java from `modules.settings.instance` → `modules.navigation.settings`. `/api/settings` path stays |
| D0h | Favorites | `DROP TABLE favorites`; also **drop the dead `settings.general.favorites*` i18n keys** (a) |
| D0i | Groups API location | **`/api/navigation/groups`** — controller moves out of registry (b) |

### Ownership audit findings (reference)

- `entry_point_groups` (V1:59-71): columns `group_key, category, name, parent_key, sort_order,
  icon, roles, hidden (V23)`. Self-FK on `parent_key`. No module linkage → navigation-owned.
- `entry_points` (V1:29-57): `module_key` FK → modules, `UNIQUE(module_key, entry_key)` →
  module-owned content, managed via registry CRUD + manifest installs. Registry-owned.
- `instance_settings` (V1:98-102): singleton `id=1` JSONB. Keys written: `homeApp`
  (`SettingsController`), feature flags (`NavigationFeaturesController`, reconciler种子
  `workspacesEnabled`). No non-nav consumers found.
- `favorites` (V1:143-149): no Java entity. Data was one-time-seeded into
  `navigation_pinned_apps` in V7:18-23. `OPTIMIZATIONS.md` already recommends the drop.

Notes:
- FK constraints *follow the renamed table by OID* — renaming `modules` does not break

  only their *names* are hygiene items.
- Column defaults via `nextval('entry_points_id_seq')` reference the sequence OID, so
  `ALTER SEQUENCE … RENAME` keeps the default working (V19 sets these defaults).

### 2.1 `V27__registry_navigation_renames.sql` (V26 was already taken by the Step-13 hygiene migration; favorites drop had already landed there)

```sql
-- === constraints (names verified via pg_constraint) ===

-- === indexes ===
-- (full list in section 1.2; pattern: ALTER INDEX <old> RENAME TO <new>;)

-- === favorites (D0h) ===
DROP TABLE IF EXISTS favorites;
```

**Step A — persisted-JSONB audit (must complete before writing V26).**
Renaming the REST JSON key `entryKey` → `contentKey` only matters for *persisted* JSON if
stored blobs embed `"entryKey":` as an object key. Audit:

| Blob | Known contents | Risk |
|---|---|---|
| `workspaces.layout` | V2 rewrote `moduleKey`/`loadPath` string values here → blob may embed tab objects | verify whether `"entryKey":` appears as *key* |
| `workspaces.groups` | same precedent (V2:52-54) | same |
| `navigation_layout.settings` | layout items are `ref` strings validated by `NavigationValidationService` | likely safe; verify |
| `navigation_user_settings.settings` | sidebar apps = `ref` strings; `ShellTreeService` derives defaults from rows | likely safe; verify |

Audit result: **zero** hits — all four blobs store string refs only; no rewrite needed (decision moot)
with guarded text replace (single deployment, Flyway runs before app boot):

```sql
UPDATE workspaces
   SET layout = replace(layout::text, '"entryKey":', '"contentKey":')::jsonb
 WHERE layout::text LIKE '%"entryKey":%';
UPDATE workspaces
   SET groups = replace(groups::text, '"entryKey":', '"contentKey":')::jsonb
 WHERE groups::text LIKE '%"entryKey":%';
-- same pattern for navigation_layout.settings / navigation_user_settings.settings if hit
```

Risk note: `replace(::text)` is a blunt instrument; guarded by the `LIKE` on the exact
`"entryKey":` token (values are kebab keys / display text and will not contain that literal).

## 8. Risks & landmines

1. Blast radius: full-depth rename touches ~30 server files + ~40 UI files + specs. Do it in
   stacked commits (schema → backend → UI → docs) inside one PR.
2. Postgres rename gaps: sequences/indexes/columns of persisted blobs — every rename listed
   in §1.2 must be explicit; leftover names surface later in `pg_constraint`/`pg_indexes`.
3. `/api/config` JSON key change breaks any consumer outside the repo UI — in-repo only
   consumer is the portal UI; risk accepted (API is Crosshubber-owned).
4. Groups controller move registry → navigation: confirm permission policy (`@PreAuthorize`)
   travels unchanged and imports don't cross feature boundaries in the wrong direction.
5. i18n key rename without V27 leaves existing tenants without the new error strings
   (reconciler seeds are insert-if-absent); old favorites keys likewise need explicit delete.
6. `workspaces` blob rewrite (2.1): guarded `replace(::text)` — re-verify dev tenant
